## 4. Current correction spike: changes

The following edits respond to the owner’s statement that both visuals and gameplay missed expectations. They are an unreviewed proposal, not an approved interpretation of the reference.

### Rules/model

In lib/game/parking_jam_model.dart:

- JamVehicle.route and capacity are now required and non-null.
- Removed the isBus distinction. Every selectable piece is a colored, passenger-serving bus with positive capacity; no generic disposable cars remain.
- Every departing bus reserves a boarding bay, and bay capacity applies to every selectable piece.
- Added tests for the all-bus rule and for a bus waiting in a stop until its passenger group reaches the front.

### Level and screen

In lib/game/parking_jam_screen.dart:

- Tutorial now has seven visible boarding bays, eight buses, and an eight-rider sequence.
- Demo now has seven bays, 12 buses, and 12 riders; route/capacity values were added to pieces that had been generic blockers.
- Replaced the flat passenger strip with a painted green oval passenger loop and riders positioned around it.
- Replaced the previous oversized bay presentation with a row of seven individual boarding bays.
- Reduced vertical whitespace and constrained the lot to available width/height, with warm pavement/green lot treatments and bus gradients/details.
- Added passenger movement animation (AnimatedPositioned) and boarding-bay transitions (AnimatedSwitcher).
- Reworded tutorial and blocker feedback in terms of colored buses rather than car IDs.

### Tests

- test/parking_jam_model_test.dart now tests all-bus gameplay and a bus waiting for matching riders.
- test/parking_jam_screen_test.dart expects the passenger loop, eight riders, seven bays, and updated feedback.

### Open design concern

The tutorial passenger sequence is interleaved by route (blue, mint, gold, coral, gold, mint, blue, coral), rather than clearly grouped into same-color passenger clusters. A grouped crowd may match the public reference imagery better, but has not been implemented. Before expanding content, determine passenger grouping, movement, queue semantics, diagonal/perspective presentation, bus directions, and whether every blocker should itself serve riders. Direct reference play is still unavailable: the emulator Play Store requested Google sign-in, and no one signed in.

### Tools and MCP recommendations already in GAME_PLAN.md

MCPs are for development and operations. The Android game must not depend on an MCP server or AI service at runtime.

- Official Dart/Flutter tooling MCP (dart mcp-server): analysis, formatting, pub.dev search, tests, runtime errors, screenshots/hot reload. Repository-scoped VS Code config exists; full IDE MCP handshake remains unverified.
- Official Firebase MCP: defer until a separate development Firebase project exists; use least privilege for configuration and crash inspection.
- GitHub MCP or available GitHub connector: optional for issue/PR triage; normal Git and GitHub Actions already cover source control and CI.
- Blender MCP: optional only if original prerendered Blender artwork is chosen. It executes Python without guards; use a disposable asset workspace.
- No unverified Play Console/AdMob publishing or payment MCP is recommended. Use official interfaces/APIs with human review.

Runtime stack recommendations include Flutter/Dart, Flutter widgets and CustomPainter for this simple puzzle, plain Dart rules and solver, versioned JSON levels, local storage, audio/haptics, Firebase adapters only after consent/privacy gates, official Google Mobile Ads with UMP for eventual ads, Play Billing through in_app_purchase, and Play Games Services only if retention evidence justifies it. Recheck current SDK and policy versions when implementing.
